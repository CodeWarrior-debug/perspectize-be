# Phase 3.4: Perspectize Branding & Glasses Identity — Research

**Researched:** 2026-02-18
**Domain:** SVG component design, JSONB preferences storage, GraphQL mutation, Svelte 5 popover UI
**Confidence:** HIGH (based on direct codebase inspection + official docs)

---

## Summary

This phase adds a glasses motif to Perspectize: a `<GlassesIcon>` Svelte 5 component, a picker popover for shape/color, JSONB preferences storage on the user table, and glasses display in the header UserSelector and AG Grid rows. The research confirms all implementation patterns from the existing codebase are directly reusable with minimal new plumbing.

The central technical concern is **SVG gradient ID uniqueness**: when the same `<GlassesIcon>` component renders multiple times on one page (header + N AG Grid rows), every instance uses the same gradient `id` in `<defs>`, causing browsers to apply the first gradient found to all instances. This must be solved explicitly.

The storage approach is straightforward: add a `preferences JSONB` nullable column to `users` via a SQL migration, store as `json.RawMessage` in the GORM model (same pattern as `ContentModel.Response`), marshal/unmarshal a `UserPreferences` Go struct. The GraphQL surface is a single `updateUserPreferences` mutation returning the updated `User`.

**Primary recommendation:** Use a single `<GlassesIcon>` Svelte component with `{#if shape === 'sunglasses'}` blocks, accept a `gradientId` prop defaulting to `crypto.randomUUID()` called at component init — this eliminates the ID collision problem with zero external dependencies. For preferences storage, use `json.RawMessage` with a typed Go struct (no `gorm.io/datatypes` package needed, it is not in go.mod).

### Pattern 1: GlassesIcon — Single Component with Shape Branches

**What:** One Svelte 5 component accepting `shape`, `color`, `size` props. Use `{#if shape === 'sunglasses'}` blocks for the three SVG shapes. Pass a unique `gradientId` to avoid cross-instance ID collisions.

**When to use:** Everywhere glasses appear (UserSelector header, AG Grid row, picker preview).

**Critical: Gradient ID uniqueness.** Each SVG `<linearGradient id="...">` must have a unique DOM ID per component instance. With multiple `<GlassesIcon>` on one page, duplicate IDs cause all instances to render the first gradient found.

**Solution: `crypto.randomUUID()` at init.**

```svelte
<!-- Source: SVG ID collision pattern (verified in browser spec) -->
<script lang="ts">
  import type { GlassesShape, GlassesColor } from '$lib/types/glasses';

  let {
    shape = 'sunglasses' as GlassesShape,
    color = 'purple' as GlassesColor,
    size = 24,
    class: className = '',
  }: {
    shape?: GlassesShape;
    color?: GlassesColor;
    size?: number;
    class?: string;
  } = $props();

  // Unique per-instance ID — avoids SVG gradient ID collision when rendered multiple times
  // crypto.randomUUID() is a browser built-in, available in secure contexts (HTTPS + localhost)
  const uid = crypto.randomUUID().replace(/-/g, '').slice(0, 8);
  const gradientId = `glasses-grad-${uid}`;

  // Color palette: each entry defines light-mode gradient stops + stroke
  const palette = {
    purple:  { light: { from: '#9F7AEA', to: '#44337A', stroke: '#44337A' }, dark: { from: '#B794F4', to: '#9F7AEA', stroke: '#9F7AEA' } },
    indigo:  { light: { from: '#7F9CF5', to: '#3730A3', stroke: '#3730A3' }, dark: { from: '#A5B4FC', to: '#6366F1', stroke: '#6366F1' } },
    teal:    { light: { from: '#4FD1C5', to: '#0D9488', stroke: '#0D9488' }, dark: { from: '#5EEAD4', to: '#14B8A6', stroke: '#14B8A6' } },
    rose:    { light: { from: '#FDA4AF', to: '#BE123C', stroke: '#BE123C' }, dark: { from: '#FECDD3', to: '#FB7185', stroke: '#FB7185' } },
    amber:   { light: { from: '#FCD34D', to: '#B45309', stroke: '#B45309' }, dark: { from: '#FDE68A', to: '#F59E0B', stroke: '#F59E0B' } },
    slate:   { light: { from: '#94A3B8', to: '#334155', stroke: '#334155' }, dark: { from: '#CBD5E1', to: '#64748B', stroke: '#64748B' } },
    emerald: { light: { from: '#6EE7B7', to: '#065F46', stroke: '#065F46' }, dark: { from: '#A7F3D0', to: '#10B981', stroke: '#10B981' } },
    sky:     { light: { from: '#7DD3FC', to: '#0369A1', stroke: '#0369A1' }, dark: { from: '#BAE6FD', to: '#38BDF8', stroke: '#38BDF8' } },
  };

  // TODO: detect dark mode via CSS media query or Tailwind dark class
  // For now: always use light mode stops (dark mode is a deferred phase)
  const c = $derived(palette[color]?.light ?? palette.purple.light);

  // ViewBox aspect ratio: each shape has its own natural aspect ratio
  const viewBox = $derived(
    shape === 'sunglasses' ? '0 0 70 28' :
    shape === 'round'      ? '0 0 56 28' :
                              '0 0 62 28'
  );
</script>

<svg
  xmlns="http://www.w3.org/2000/svg"
  viewBox={viewBox}
  width={size}
  height={size}
  aria-hidden="true"
  class={className}
>
  <defs>
    <linearGradient id={gradientId} x1="0" y1="0" x2="0.2" y2="1">
      <stop offset="0%" stop-color={c.from} stop-opacity={shape === 'sunglasses' ? 0.5 : 0.45} />
      <stop offset="100%" stop-color={c.to} stop-opacity={shape === 'sunglasses' ? 0.9 : 0.85} />
    </linearGradient>
  </defs>

  {#if shape === 'sunglasses'}
    <!-- C1 Sunglasses — viewBox 70x28 -->
    <path d="M10 8 L30 7 Q34 7 34 10.5 L33 17 Q32 21 28 21 L14 21 Q10 21 9 17 L8 10.5 Q8 8 10 8 Z"
      fill="url(#{gradientId})" stroke={c.stroke} stroke-width="1.4" stroke-linejoin="round"/>
    <path d="M38 8 L58 7 Q62 7 62 10.5 L61 17 Q60 21 56 21 L42 21 Q38 21 37 17 L36 10.5 Q36 8 38 8 Z"
      fill="url(#{gradientId})" stroke={c.stroke} stroke-width="1.4" stroke-linejoin="round"/>
    <path d="M34 10 Q36 8 36 10" fill="none" stroke={c.stroke} stroke-width="1.4" stroke-linecap="round"/>
    <line x1="8" y1="9.5" x2="3" y2="7" stroke={c.stroke} stroke-width="1.4" stroke-linecap="round"/>
    <line x1="62" y1="9.5" x2="67" y2="7" stroke={c.stroke} stroke-width="1.4" stroke-linecap="round"/>
  {:else if shape === 'round'}
    <!-- Teddy A — Round Pince-nez — viewBox 56x28 -->
    <circle cx="14" cy="14" r="11" fill="url(#{gradientId})" stroke={c.stroke} stroke-width="1.5"/>
    <circle cx="42" cy="14" r="11" fill="url(#{gradientId})" stroke={c.stroke} stroke-width="1.5"/>
    <path d="M25 11 Q28 6 31 11" fill="none" stroke={c.stroke} stroke-width="1.5" stroke-linecap="round"/>
  {:else}
    <!-- Teddy B — Oval Pince-nez — viewBox 62x28 -->
    <ellipse cx="16" cy="14" rx="13" ry="10" fill="url(#{gradientId})" stroke={c.stroke} stroke-width="1.5"/>
    <ellipse cx="48" cy="14" rx="13" ry="10" fill="url(#{gradientId})" stroke={c.stroke} stroke-width="1.5"/>
    <path d="M29 11 Q32 5 35 11" fill="none" stroke={c.stroke} stroke-width="1.5" stroke-linecap="round"/>
  {/if}
</svg>
```

**Svelte 5 note:** `uid` is computed once at module init — not reactive. This is correct; the value should never change per component lifetime.

**viewBox / size interaction:** The three shapes have different natural aspect ratios (70:28, 56:28, 62:28). Setting `width={size} height={size}` with `preserveAspectRatio` default (`xMidYMid meet`) will letterbox the shapes. Use `height={size}` only and let width be `auto`, or compute aspect-correct width per shape. Recommended: pass `size` as a height reference and let SVG scale naturally.

### Pattern 2: GlassesPickerPopover — Custom Popover (Not FormPopover)

**What:** The glasses picker is NOT a form (no text inputs, no submit button in the traditional sense). It uses the raw `Popover/PopoverTrigger/PopoverContent` primitives directly — not `FormPopover`.

**When to use:** Triggered from UserSelector avatar click. Also shown on first-time user selection (onboarding).

```svelte
<!-- GlassesPickerPopover.svelte — simplified structure -->
<script lang="ts">
  import { Popover, PopoverTrigger, PopoverContent } from '$lib/components/shadcn';
  import GlassesIcon from '$lib/components/GlassesIcon.svelte';
  import { useUpdateGlassesPreference } from '$lib/queries/hooks/useUpdateGlassesPreference';
  import type { GlassesShape, GlassesColor } from '$lib/types/glasses';

  let {
    userId,
    initialShape = 'sunglasses' as GlassesShape,
    initialColor = 'purple' as GlassesColor,
    open = $bindable(false),
    onDismiss,
  }: {
    userId: number;
    initialShape?: GlassesShape;
    initialColor?: GlassesColor;
    open?: boolean;
    onDismiss?: () => void;
  } = $props();

  let selectedShape = $state<GlassesShape>(initialShape);
  let selectedColor = $state<GlassesColor>(initialColor);

  const mutation = useUpdateGlassesPreference();

  function save() {
    mutation.mutate({ userId, shape: selectedShape, color: selectedColor });
    open = false;
  }
</script>

<Popover bind:open>
  <PopoverTrigger>
    <GlassesIcon shape={initialShape} color={initialColor} size={20} />
  </PopoverTrigger>
  <PopoverContent align="end" sideOffset={8} class="w-64">
    <!-- Live preview -->
    <div class="flex justify-center mb-4">
      <GlassesIcon shape={selectedShape} color={selectedColor} size={40} />
    </div>

    <!-- Shape toggle: 3 mini previews as clickable cards -->
    <div class="flex gap-2 mb-4">
      {#each ['sunglasses', 'round', 'oval'] as shape (shape)}
        <button
          class="flex-1 rounded border p-2 flex justify-center {selectedShape === shape ? 'border-primary bg-accent' : 'border-border'}"
          onclick={() => selectedShape = shape as GlassesShape}
          aria-pressed={selectedShape === shape}
        >
          <GlassesIcon {shape} color={selectedColor} size={20} />
        </button>
      {/each}
    </div>

    <!-- Color swatches: 8 colored circles -->
    <div class="flex gap-2 flex-wrap mb-4">
      {#each PALETTE_ENTRIES as entry (entry.key)}
        <button
          class="w-7 h-7 rounded-full border-2 {selectedColor === entry.key ? 'border-foreground' : 'border-transparent'}"
          style="background: {entry.swatch};"
          onclick={() => selectedColor = entry.key}
          aria-label={entry.key}
          aria-pressed={selectedColor === entry.key}
        />
      {/each}
    </div>

    <!-- Actions -->
    <div class="flex gap-2 justify-end">
      {#if onDismiss}
        <button class="text-sm text-muted-foreground" onclick={onDismiss}>Skip</button>
      {/if}
      <button class="..." onclick={save} disabled={mutation.isPending}>Save</button>
    </div>
  </PopoverContent>
</Popover>
```

**Shape toggle UX recommendation (Claude's discretion):** Use **mini icon cards** (three small `<GlassesIcon>` previews in a row, each a clickable card with active border). This is more expressive than radio buttons or text labels, and works naturally at the popover width of `w-64`. Each card is ~20px tall glasses rendered at natural aspect ratio.

**Color swatch UX recommendation:** 8 circles, ~28px diameter, with a border indicator for selected state. Swatch background is the light-mode "from" gradient stop color for visual recognition. No labels needed — color names accessible via `aria-label`.

```go
type GlassesShape string

const (
    GlassesShapeSunglasses GlassesShape = "SUNGLASSES"
    GlassesShapeRound      GlassesShape = "ROUND"
    GlassesShapeOval       GlassesShape = "OVAL"
)

// GlassesColor is the named palette color for glasses
type GlassesColor string

const (
    GlassesColorPurple  GlassesColor = "purple"
    GlassesColorIndigo  GlassesColor = "indigo"
    GlassesColorTeal    GlassesColor = "teal"
    GlassesColorRose    GlassesColor = "rose"
    GlassesColorAmber   GlassesColor = "amber"
    GlassesColorSlate   GlassesColor = "slate"
    GlassesColorEmerald GlassesColor = "emerald"
    GlassesColorSky     GlassesColor = "sky"
)

// GlassesPreference stores user's selected glasses configuration
type GlassesPreference struct {
    Shape GlassesShape `json:"shape"`
    Color GlassesColor `json:"color"`
}

// UserPreferences is the top-level JSONB structure for the preferences column.
// Extensible: future fields (theme, typography) added here without schema migration.
type UserPreferences struct {
    Glasses *GlassesPreference `json:"glasses,omitempty"`

```

**Mapper pattern (matches existing userModelToDomain / userDomainToModel):**

```go
// In gorm_mappers.go — extend userModelToDomain to parse preferences
func parseUserPreferences(raw json.RawMessage) *domain.UserPreferences {
    if len(raw) == 0 || string(raw) == "null" {
        return nil
    }
    var prefs domain.UserPreferences
    if err := json.Unmarshal(raw, &prefs); err != nil {
        slog.Warn("failed to parse user preferences JSON", "error", err)
        return nil
    }
    return &prefs
}
```

**Repository update method:** Add `UpdatePreferences(ctx, userID int, prefs *domain.UserPreferences) error` to `UserRepository` interface + `GormUserRepository` impl.

```go
// gorm_user_repository.go
func (r *GormUserRepository) UpdatePreferences(ctx context.Context, userID int, prefs *domain.UserPreferences) error {
    data, err := json.Marshal(prefs)
    if err != nil {
        return fmt.Errorf("failed to marshal preferences: %w", err)
    }
    result := r.db.WithContext(ctx).Model(&UserModel{}).
        Where("id = ?", userID).
        Update("preferences", json.RawMessage(data))
    if result.Error != nil {
        return result.Error
    }
    if result.RowsAffected == 0 {
        return domain.ErrNotFound
    }
    return nil
}
```

**WARNING: GORM and json.RawMessage updates.** GORM's `Updates(map[string]interface{})` with `json.RawMessage` can be tricky — use `Update("preferences", gorm.Expr("?::jsonb", string(data)))` or the column-specific `Update("preferences", rawMessage)`. Verify with a targeted integration test.

### Pattern 5: Frontend Query Hook

**What:** New `useUpdateGlassesPreference` mutation hook, following `useCreateUser` pattern exactly.

```typescript
// frontend/src/lib/queries/hooks/useUpdateGlassesPreference.ts
import { createMutation, useQueryClient } from '@tanstack/svelte-query';
import { toast } from 'svelte-sonner';
import { graphqlClient } from '../client';
import { UPDATE_GLASSES_PREFERENCE, type UpdateGlassesPreferenceInput } from '../users';
import { queryKeys } from '../keys';

export function useUpdateGlassesPreference() {
  const queryClient = useQueryClient();

  return createMutation(() => ({
    mutationFn: async (input: UpdateGlassesPreferenceInput) =>
      graphqlClient.request(UPDATE_GLASSES_PREFERENCE, { input }),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: queryKeys.users.list() });
    },
    onError: () => {
      toast.error('Failed to save glasses preference.');
    },
  }));
}
```

**Query key note:** The `users.list()` invalidation refreshes the UserSelector. If individual user detail queries are added to the keys factory later, also invalidate `queryKeys.users.detail(userId)`.

### Pattern 6: Onboarding Trigger in UserSelector

**What:** Detect first-time user selection → show glasses picker. Store "has onboarded" flag in `sessionStorage` (same mechanism as `selectedUserId`).

**Implementation strategy:** Add a reactive `$effect` in `UserSelector.svelte` that fires when `selectedValue` changes from null to a value for the first time per session. Show the `GlassesPickerPopover` with `onDismiss` callback.

```svelte
<!-- UserSelector.svelte — add onboarding detection -->
let glassesPickerOpen = $state(false);
const hasOnboarded = $derived(() => {
  if (!browser) return true;
  return sessionStorage.getItem('perspectize:hasOnboarded') === 'true';
});

$effect(() => {
  // Trigger when user is selected for first time this session
  if (selectedValue && !hasOnboarded()) {
    glassesPickerOpen = true;
  }
});

function handleOnboardingDismiss() {
  glassesPickerOpen = false;
  sessionStorage.setItem('perspectize:hasOnboarded', 'true');
}
```

**Note:** After onboarding is complete (save clicked), also set the `hasOnboarded` session flag.

### Pattern 7: Default Glasses on User Creation

**What:** When a user is created, assign a random shape + purple color as default preference. This happens in the backend `UserService.Create` method, or can be set client-side immediately after `createUser` succeeds.

**Recommended approach: client-side default on creation.**  After `useCreateUser` `onSuccess`, immediately fire `useUpdateGlassesPreference` with a random shape + 'purple'. This avoids touching the backend Create path and keeps the backend simpler. The random shape can be selected from `['SUNGLASSES', 'ROUND', 'OVAL']` using `Math.random()`.

**Alternative: backend default in service.** Set `Preferences.Glasses` in `UserService.Create` before persisting. Cleaner data integrity guarantee. Either works; client-side is simpler to implement without rippling service/test changes.

### Anti-Patterns to Avoid

- **Hardcoded gradient IDs:** Never use fixed IDs like `id="glasses-grad"` in a component that renders more than once. The first rendered instance wins in browsers.
- **Using `{@html}` with raw SVG strings:** Avoids Svelte's reactivity. Use template syntax `{#if}` blocks instead.
- **gorm.io/datatypes for JSONB:** Package is not in go.mod. Use `json.RawMessage` with `gorm:"type:jsonb"` tag — same as `ContentModel.Response`.
- **Using FormPopover for glasses picker:** FormPopover wraps a form with Submit/Cancel. The glasses picker is a live-preview picker with auto-save semantics — use raw Popover primitives.
- **Separate SVG components per shape (Teddy A, Teddy B, C1):** Three separate components creates unnecessary file proliferation for three shapes. Use `{#if}` branches in one component; refactor if shapes grow beyond ~5.
- **Storing glasses shape as DB enum:** The `preferences JSONB` approach is more extensible. Avoid adding `glasses_shape` and `glasses_color` as separate columns.

## Common Pitfalls

### Pitfall 1: SVG Gradient ID Collision (Critical)

**What goes wrong:** Multiple `<GlassesIcon>` instances on the same page all declare `<linearGradient id="glasses-grad">`. Browsers resolve `fill="url(#glasses-grad)"` to the first matching ID in the DOM, so all glasses render with the gradient from the first instance only. When that instance is removed (e.g., the header user changes), all other glasses lose their gradient.

**Why it happens:** SVG gradient IDs are global DOM IDs, not scoped to the SVG element.

**How to avoid:** Generate a per-instance unique ID at component initialization using `crypto.randomUUID()`. Use this ID in both `<linearGradient id={gradientId}>` and `fill="url(#{gradientId})"`.

**Warning signs:** All glasses look identical regardless of color selection, or glasses in the table row look like the header glasses.

### Pitfall 2: GORM json.RawMessage Update Behavior

**What goes wrong:** `db.Model(&UserModel{}).Updates(map[string]interface{}{"preferences": rawMessage})` may not serialize correctly — GORM may treat `json.RawMessage` as `[]byte` and escape it as a base64 string in some driver configurations.

**Why it happens:** GORM's generic `Updates` path doesn't always recognize custom types.

**How to avoid:** Use `Update("preferences", gorm.Expr("?::jsonb", string(data)))` to pass the JSON string and cast it explicitly in PostgreSQL. Alternatively, use a targeted `Save` on the full model (less surgical but reliable).

**Warning signs:** `preferences` column stores a base64 string instead of JSON object; GraphQL query returns a string instead of an object for `preferences`.

### Pitfall 3: UserRepository Interface Mock Updates

**What goes wrong:** Adding `UpdatePreferences` to `UserRepository` interface causes all tests implementing `mockUserRepository` to fail compilation.

**Why it happens:** Go interfaces require all methods to be implemented. The `user_service_test.go` mock `mockUserRepository` struct implements all `UserRepository` methods. Adding a new method breaks the compile.

**How to avoid:** After updating the `UserRepository` interface, search for all `mockUserRepository` implementations with `grep -r "mockUserRepository" backend/test/` and add stub `UpdatePreferences` methods.

**Warning signs:** `go build ./...` fails with "does not implement UserRepository (missing UpdatePreferences method)".

### Pitfall 4: gqlgen Model Staleness

**What goes wrong:** Adding fields to `schema.graphql` without running `make graphql-gen` causes resolver compilation errors (generated model doesn't have the new field).

**Why it happens:** gqlgen generates `models_gen.go` from the schema. The generated file must be regenerated after schema changes.

**How to avoid:** Always run `make graphql-gen` after any schema change, before writing resolver code.

**Warning signs:** `cannot use ... (type model.User) as type ...` errors referencing the `Preferences` field.

### Pitfall 5: Svelte 5 Effect for Derivation

**What goes wrong:** Using `$effect` to compute the active gradient colors from the `color` prop instead of `$derived`.

**Why it happens:** Habit from Svelte 4 reactive statements.

**How to avoid:** Use `const c = $derived(palette[color]?.light ?? palette.purple.light)`. The CLAUDE.md for the frontend explicitly forbids `$effect` for derivation.

### Pitfall 6: Popover Width Too Narrow

**What goes wrong:** The default `PopoverContent` has `w-72` (288px). The glasses picker with 3 shape cards + 8 color swatches may feel cramped at 288px.

**Why it happens:** Default shadcn popover width.

**How to avoid:** Override with `class="w-64"` or `class="w-72"` (test in browser). The shape cards can be `flex-1` in a 3-item row at any width above ~180px. Color swatches at 7+2px gap each fit 8 across at ~230px+.

```typescript
      },
    });
  }
  return eGui;
}
```

## Open Questions

1. **Dark mode glasses variants**
   - What we know: The SVG reference file defines light/dark mode variants with different gradient stops. The current `app.css` has no dark mode tokens (only light mode). The CONTEXT.md defers app-wide dark mode to a future phase.
   - What's unclear: Should the `GlassesIcon` component detect dark mode now (even if the app doesn't support it yet), or always use light mode stops?
   - Recommendation: Always use light mode stops for now. Add a `darkMode` boolean prop later when dark mode theming lands. This avoids complexity with no user-visible benefit.

2. **Random default shape on user creation: client vs. server**
   - What we know: Both approaches work. Client-side fires a second mutation after `createUser` succeeds.
   - What's unclear: Server-side is cleaner for data integrity (preferences always set at creation), but requires touching `UserService.Create` + migration default logic.
   - Recommendation: Client-side random assignment after `createUser` is simpler and keeps backend Create path unchanged. If server-side is preferred for correctness, set in `UserService.Create` using `math/rand`.

3. **AG Grid Svelte 5 mount() API for cell renderers**
   - What we know: `mount()` is the Svelte 5 API for imperative mounting. The existing `itemCellRenderer` in `formatting.ts` does not use Svelte components — it manipulates DOM directly.
   - What's unclear: Whether `mount()` in AG Grid cell renderers causes memory leaks if `destroy()` is not called.
   - Recommendation: Keep glasses column renderer as direct DOM manipulation with a plain `<svg>` element (not a mounted Svelte component). This avoids the lifecycle complexity. Use a `createGlassesSVGElement(shape, color, size)` helper that returns a DOM element directly.

4. **preferences field in the users GraphQL query**
   - What we know: The `LIST_USERS` query in `users.ts` currently fetches only `id` and `username`. To display glasses, it needs `preferences` too.
   - What's unclear: Whether returning `preferences` for all users in the list query is the right approach, or whether a separate user detail query should be used.
   - Recommendation: Add `preferences` to the `LIST_USERS` query and the `User` GraphQL type. The payload is small (a JSON object with 2 string fields). This keeps the existing query shape.
