# Phase 3.5: Google NL Taxonomy Research Spike - Research

**Researched:** 2026-02-20
**Domain:** Google Cloud Natural Language API Content Classification / Taxonomy
**Confidence:** HIGH (official docs verified)

## Summary

The Google Cloud Natural Language API provides a `classifyText` method that classifies text into a hierarchical taxonomy of content categories. The V2 model (GA since January 2023) supports **1091 content categories** organized up to **5 levels deep**, using forward-slash-delimited paths like `/Sports/Team Sports/American Football`. The taxonomy is a superset of the older V1 model (which had ~700 categories).

For Perspectize, this taxonomy provides an excellent foundation for hierarchical content categorization. The API can classify YouTube video metadata (title + description concatenated) into these categories with confidence scores. The key challenge is transforming Google's path format (`/Arts & Entertainment/Music & Audio`) into PostgreSQL ltree-compatible paths (`arts_and_entertainment.music_and_audio`), since ltree only allows `A-Za-z0-9_-` in labels and uses `.` as the separator.

The user's plan to use Claude Haiku for auto-classification ($0.031/month) remains the better production approach, but the Google NL API is invaluable for **taxonomy discovery** -- using it to explore what categories exist and how deep they go, then curating a subset for the Perspectize categories table.

**Primary recommendation:** Use the Google NL API `classifyText` endpoint interactively (via Postman) to discover the full taxonomy tree, then curate a subset of ~50-100 categories relevant to YouTube content rating. Store these with ltree paths in PostgreSQL.

- Categories with confidence > 0.5 are strong matches
- Categories with confidence 0.1-0.5 are related but secondary
- Categories with confidence < 0.1 are tangential (V2 may return many of these)

- Collect all unique category paths from your exploration
- Decide which ones are relevant to your app
- Create ltree-compatible paths (see transformation rules below)

## Architecture Patterns

### Pattern 1: Google NL Path to PostgreSQL ltree Transformation

**What:** Google NL categories use paths like `/Arts & Entertainment/Music & Audio/Classical Music`. PostgreSQL ltree requires labels matching `[A-Za-z0-9_-]` separated by `.` dots.

**Transformation rules:**
1. Remove leading `/`
2. Replace `/` with `.` (level separator)
3. Replace ` & ` with `_and_`
4. Replace ` ` (space) with `_`
5. Replace `,` with empty string
6. Convert to lowercase
7. Remove any remaining non-alphanumeric characters except `_` and `-`

**Examples:**

| Google NL Path | ltree Path |
|----------------|------------|
| `/Sports` | `sports` |
| `/Sports/Team Sports` | `sports.team_sports` |
| `/Sports/Team Sports/American Football` | `sports.team_sports.american_football` |
| `/Arts & Entertainment` | `arts_and_entertainment` |
| `/Arts & Entertainment/Music & Audio/Classical Music` | `arts_and_entertainment.music_and_audio.classical_music` |
| `/Science/Computer Science/Machine Learning & Artificial Intelligence` | `science.computer_science.machine_learning_and_artificial_intelligence` |

**Go transformation function:**
```go
import (
    "strings"
    "regexp"
)

var nonAlphanumeric = regexp.MustCompile(`[^a-z0-9_-]`)

// GoogleNLPathToLtree converts a Google NL category path to a PostgreSQL ltree path.
func GoogleNLPathToLtree(googlePath string) string {
    // Remove leading slash
    path := strings.TrimPrefix(googlePath, "/")
    // Replace slash separators with dots
    path = strings.ReplaceAll(path, "/", ".")
    // Replace ampersands
    path = strings.ReplaceAll(path, " & ", "_and_")
    // Replace spaces
    path = strings.ReplaceAll(path, " ", "_")
    // Remove commas
    path = strings.ReplaceAll(path, ",", "")
    // Lowercase
    path = strings.ToLower(path)
    // Remove any remaining invalid characters
    path = nonAlphanumeric.ReplaceAllString(path, "")
    return path
}
```

### Pattern 2: Category Table Schema with ltree

```sql
-- Enable ltree extension
CREATE EXTENSION IF NOT EXISTS ltree;

-- Categories table (both Google NL taxonomy and user-created)
CREATE TABLE categories (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        TEXT NOT NULL,              -- Display name: "American Football"
    slug        TEXT NOT NULL UNIQUE,       -- URL-safe: "american-football"
    path        ltree NOT NULL,             -- Hierarchy: "sports.team_sports.american_football"
    source      TEXT NOT NULL DEFAULT 'google_nl',  -- 'google_nl' or 'user'
    google_path TEXT,                       -- Original: "/Sports/Team Sports/American Football"
    depth       INT GENERATED ALWAYS AS (nlevel(path)) STORED,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- GiST index for hierarchical queries (ancestor/descendant)
CREATE INDEX idx_categories_path_gist ON categories USING GIST (path);

-- B-tree index for exact path lookups
CREATE INDEX idx_categories_path_btree ON categories USING BTREE (path);

-- Unique constraint on path
CREATE UNIQUE INDEX idx_categories_path_unique ON categories (path);
```

### Pattern 3: Hierarchical Queries with ltree

```sql
-- Get all descendants of Sports (any depth)
SELECT * FROM categories WHERE path <@ 'sports';

-- Get only direct children of Sports (depth = parent + 1)
SELECT * FROM categories
WHERE path <@ 'sports' AND nlevel(path) = nlevel('sports') + 1;

-- Get ancestors of a specific category
SELECT * FROM categories WHERE path @> 'sports.team_sports.american_football';

-- Get siblings (same parent)
SELECT * FROM categories
WHERE path <@ subpath('sports.team_sports.american_football', 0, -1)
  AND nlevel(path) = nlevel('sports.team_sports.american_football');

-- Get the breadcrumb path for display
SELECT name FROM categories
WHERE path @> 'sports.team_sports.american_football'
ORDER BY nlevel(path);
-- Returns: "Sports", "Team Sports", "American Football"
```

### Pattern 4: User-Created Categories Coexisting with Google NL Taxonomy

```sql
-- User adds a custom category under an existing Google NL category
INSERT INTO categories (name, slug, path, source) VALUES
('Chiefs', 'chiefs', 'sports.team_sports.american_football.chiefs', 'user');

-- User adds a top-level custom category
INSERT INTO categories (name, slug, path, source) VALUES

-- User adds a sub-category under their custom category
INSERT INTO categories (name, slug, path, source) VALUES
('Hot Takes', 'hot-takes', 'reactions.hot_takes', 'user');
```

**Rule:** User categories use the same table and same ltree hierarchy. They can extend Google NL categories at any depth or create entirely new top-level trees.

### Anti-Patterns to Avoid

- **Don't store the full `/` path as the ltree value.** ltree uses `.` separators and has character restrictions. Always transform.
- **Don't skip the `source` column.** You need to distinguish Google NL seed data from user-created categories for display, editing permissions, and sync.
- **Don't create separate tables for Google vs. user categories.** Same table, same hierarchy, same queries.
- **Don't use the Google NL API for production auto-classification.** At $2/1000 units it's more expensive than Claude Haiku. Use the API only for taxonomy exploration.

## Common Pitfalls

### Pitfall 1: ltree Character Restrictions

**What goes wrong:** Google NL paths contain spaces, ampersands, commas, and parentheses. Inserting these directly into ltree fails.
**Why it happens:** ltree only allows `A-Za-z0-9_-` in labels.
**How to avoid:** Always use the transformation function. Store the original Google NL path in a separate `google_path` column for reference.
**Warning signs:** PostgreSQL errors like `invalid ltree` on INSERT.

### Pitfall 2: Minimum Token Requirement

**What goes wrong:** classifyText returns an error for short text.
**Why it happens:** The API requires at least 20 tokens (words) for classification.
**How to avoid:** Concatenate title + description + tags. If still under 20 words, pad with channel name and video metadata.
**Warning signs:** `400 Bad Request` with message about minimum content length.

### Pitfall 3: V1 vs V2 Model Confusion

**What goes wrong:** V1 model returns only the most specific category. V2 returns all matching categories including parents.
**Why it happens:** Different filtering behavior between model versions.
**How to avoid:** Always use V2 for taxonomy discovery. Use V1 if you only want the single best match.
**Warning signs:** Getting only 1 category back when you expected a hierarchy.

### Pitfall 4: Over-Granular Category Seeding

**What goes wrong:** Importing all 1091 categories creates an unwieldy, mostly-empty category tree.
**Why it happens:** Most of the 1091 categories are irrelevant to YouTube content rating.
**How to avoid:** Curate to ~50-100 categories relevant to YouTube. Seed only 2-3 levels deep initially. Let users extend deeper.
**Warning signs:** Category picker has hundreds of empty categories nobody uses.

### Pitfall 5: Confidence Score Thresholds

**What goes wrong:** Auto-classification assigns wrong categories because threshold is too low.
**Why it happens:** V2 model returns many categories with low confidence (0.01-0.1).
**How to avoid:** Use a minimum confidence threshold of 0.5 for primary category assignment. Treat 0.3-0.5 as suggestions requiring user confirmation.
**Warning signs:** Content miscategorized, users constantly re-categorizing.

## Open Questions

1. **Exact subcategory paths for specific sports**
   - What we know: The taxonomy has `/Sports/Team Sports/American Football`, `/Sports/Team Sports/Basketball`, etc.
   - What's unclear: Whether NFL, NBA, MLB etc. exist as further subcategories, or if those are too specific for the Google taxonomy
   - Recommendation: Use the API curls to test with specific team/league content and see what comes back. User-created categories can fill gaps (e.g., `sports.team_sports.american_football.nfl.chiefs`)

2. **Full V2 category list programmatic extraction**
   - What we know: 1091 categories exist, documented at https://cloud.google.com/natural-language/docs/categories
   - What's unclear: Whether there's an API to list all categories without classifying text
   - Recommendation: There is no "list categories" endpoint. Discovery must happen through classifying diverse text samples. The categories page in the docs is the canonical reference.

3. **V2 model via V2 API endpoint**
   - What we know: V1 endpoint (`/v1/documents:classifyText`) supports V2 model via `classificationModelOptions`. V2 endpoint (`/v2/documents:classifyText`) exists but has different request schema.
   - What's unclear: Whether V2 endpoint requires different auth or has different behavior
   - Recommendation: Use V1 endpoint with V2 model options (as shown in curls above). This is the documented, well-tested approach.
