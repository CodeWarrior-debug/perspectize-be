# Phase 03.5.1: Wikidata Category Attribution - Research

**Researched:** 2026-02-28
**Domain:** Wikidata Entity Search API, Go HTTP client, PostgreSQL schema, GraphQL, AG Grid typeahead
**Confidence:** HIGH

## Summary

This phase implements a Wikidata-backed category system for content items in Perspectize. The user manually searches Wikidata entities via a typeahead in the AG Grid ActivityTable, selects one as the content's primary category. Categories are cached locally in a `categories` table keyed by Wikidata Q-ID.

The implementation is a well-scoped full-stack feature touching all layers of the hexagonal architecture: new domain model (Category), new port interface (CategoryRepository), new adapter (Wikidata HTTP client + GORM repository), new service (CategoryService), GraphQL schema additions, a database migration, and a frontend AG Grid column with typeahead popover.

The Wikidata `wbsearchentities` API is free, requires no authentication, and returns structured entity data (Q-ID, label, description, entity type). The main risks are rate limiting (be polite with User-Agent) and ensuring the typeahead UX is responsive despite the external API call.

**Primary recommendation:** Follow the existing hexagonal architecture patterns exactly. The Wikidata client mirrors the YouTube client pattern. The Category domain model, GORM model, repository, and service follow established conventions. The AG Grid column uses a custom cell renderer + popover, similar to the existing Perspectize column pattern.

### Pattern 1: Wikidata HTTP Client (mirrors YouTube client)

**What:** Go HTTP client wrapping the Wikidata `wbsearchentities` API endpoint.
**When to use:** Any time the frontend needs to search Wikidata entities.

```go
// Source: Existing YouTube client pattern (backend/internal/adapters/youtube/client.go)
package wikidata

import (
    "context"
    "encoding/json"
    "fmt"
    "io"
    "log/slog"
    "net/http"
    "net/url"
    "time"
)

type Client struct {
    httpClient *http.Client
    baseURL    string
    userAgent  string
}

func NewClient() *Client {
    return &Client{
        httpClient: &http.Client{
            Timeout: 10 * time.Second,
        },
        baseURL:   "https://www.wikidata.org/w/api.php",
        userAgent: "Perspectize/1.0 (https://github.com/CodeWarrior-debug/perspectize)",
    }
}

type SearchResult struct {
    QID         string `json:"id"`
    Label       string `json:"label"`
    Description string `json:"description"`
    // Match.Type can be "label" or "alias"
}
```

### Pattern 3: Category Assignment via Mutation (SetPrimaryCategory)

**What:** A mutation that upserts the category then assigns it to content.
**When to use:** When user selects a Wikidata result from the typeahead.

The flow:
1. Frontend calls `setPrimaryCategory(contentId, qid, label, description, entityType)`
2. Resolver calls CategoryService.SetPrimaryCategory()
3. Service upserts category (by wikidata_qid) into categories table
4. Service updates content.primary_category_id FK
5. Returns updated Content with populated primaryCategory field

### Anti-Patterns to Avoid
- **Direct Wikidata calls from frontend:** Always proxy through backend to enforce User-Agent and rate limits
- **Storing full Wikidata entity data:** Only store Q-ID, label, description, entity_type (light cache)
- **Creating separate resolver files:** gqlgen follow-schema layout puts all resolvers in schema.resolvers.go; don't create separate category_resolver.go
- **Using AG Grid cell editor for typeahead:** Cell editors don't support popover/portal rendering well; use the onCellClicked + external popover pattern instead (same as Perspectize column)
- **Fetching categories as nested Content field via SQL JOIN:** Use a separate query or field resolver to avoid N+1; or accept the simple LEFT JOIN approach since primary_category is a single FK

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTTP retry with backoff | Custom retry loop | Simple retry function (3 attempts, 1s/2s/4s backoff) | Keep it minimal -- Wikidata is reliable, retries are edge-case insurance |
| Debounced search | Custom debounce timer | `setTimeout`/`clearTimeout` in `$effect` or query `enabled` guard | Same pattern used in ActivityTable filter debounce (500ms) |
| Upsert logic | Manual SELECT + INSERT | GORM `clause.OnConflict` with `DoUpdates` on wikidata_qid | Same pattern as GetOrCreateByURL in content repository |
| Query key management | Ad-hoc query keys | `queryKeys` factory in `keys.ts` | Established pattern for hierarchical cache invalidation |

**Key insight:** Every piece of this feature has an existing pattern in the codebase. The Wikidata client mirrors YouTube client. The CategoryRepository mirrors ContentRepository. The AG Grid column mirrors existing columns. The mutation hook mirrors useAddVideo.

## Common Pitfalls

### Pitfall 1: Missing User-Agent Header
**What goes wrong:** Wikidata blocks requests without a proper User-Agent header (returns 403 or error JSON).
**Why it happens:** Go's default `http.Client` doesn't set User-Agent by default.
**How to avoid:** Set `User-Agent` header on every request in the Wikidata client. Format: `Perspectize/1.0 (https://github.com/CodeWarrior-debug/perspectize; contact@email.com)`.
**Warning signs:** 403 responses or `{"error":{"code":"badagent"}}` from Wikidata.

### Pitfall 2: Wikidata API Response Shape Surprises
**What goes wrong:** The `wbsearchentities` response has both deprecated flat fields (`label`, `description`) and newer `display` object with richer structure.
**Why it happens:** Wikidata added `display` field later but kept backward-compatible flat fields.
**How to avoid:** Use the flat `label` and `description` fields (simpler, still supported). They contain the same data for single-language requests.
**Warning signs:** Confusing struct definitions trying to map both `display.label.value` and top-level `label`.

### Pitfall 3: AG Grid Popover Portal Positioning
**What goes wrong:** Popover renders inside AG Grid's clipping container and gets cut off.
**Why it happens:** AG Grid cells have `overflow: hidden`.
**How to avoid:** Render the popover outside the grid (same pattern as PerspectivePopover): track click state, render popover component below the grid div in the template.
**Warning signs:** Popover appearing clipped or invisible.

### Pitfall 4: Category Column N+1 Query
**What goes wrong:** If Content.primaryCategory is resolved via a field resolver, each content item triggers a separate DB query.
**Why it happens:** GraphQL nested field resolution without batching.
**How to avoid:** Two options: (a) LEFT JOIN categories in the content List query, or (b) add a simple batch loader. For this phase, option (a) is simpler since it's a single FK. Add `primary_category_id` to ContentModel and LEFT JOIN or Preload in GORM.
**Warning signs:** Slow content list queries when many items have categories.

### Pitfall 5: Race Condition on Category Upsert
**What goes wrong:** Two users select the same Wikidata entity simultaneously, causing a unique constraint violation.
**Why it happens:** TOCTOU race between checking existence and inserting.
**How to avoid:** Use GORM `clause.OnConflict` with `DoUpdates` on `wikidata_qid` column (same pattern as content URL upsert). This makes the upsert atomic.
**Warning signs:** Sporadic "duplicate key" errors in logs.

### Pitfall 6: Typeahead Fires on Every Keystroke
**What goes wrong:** Hundreds of Wikidata API requests per second while user types.
**Why it happens:** No debounce or minimum character threshold.
**How to avoid:** (a) Minimum 2 characters before querying, (b) 300ms debounce, (c) TanStack Query `enabled` guard prevents queries for short strings. The existing ActivityTable uses 500ms debounce for filter changes.
**Warning signs:** Console spam of network requests, Wikidata rate limiting (429 responses).

### Pitfall 7: Content Model Primary Category ID Migration
**What goes wrong:** Forgetting to add `primary_category_id` to the GORM ContentModel, causing it to be invisible to queries.
**Why it happens:** The migration adds the column, but GORM needs the struct field too.
**How to avoid:** Add `PrimaryCategoryID *int` to ContentModel and update both mappers (contentModelToDomain, contentDomainToModel). Also update domain.Content to include PrimaryCategoryID.
**Warning signs:** Category assignment succeeds but Content.primaryCategory always returns null.

### Go Wikidata Client Implementation

```go
// Source: Modeled after backend/internal/adapters/youtube/client.go
package wikidata

type SearchResponse struct {
    SearchInfo struct {
        Search string `json:"search"`
    } `json:"searchinfo"`
    Search []SearchEntity `json:"search"`
    Success int           `json:"success"`
}

type SearchEntity struct {
    ID          string `json:"id"`
    Label       string `json:"label"`
    Description string `json:"description"`
    URL         string `json:"url"`
    Match       struct {
        Type     string `json:"type"`
        Language string `json:"language"`
        Text     string `json:"text"`
    } `json:"match"`
}

func (c *Client) Search(ctx context.Context, query, language string, limit int) ([]SearchEntity, error) {
    params := url.Values{
        "action":   {"wbsearchentities"},
        "search":   {query},
        "language": {language},
        "format":   {"json"},
        "type":     {"item"},
        "limit":    {strconv.Itoa(limit)},
    }

    endpoint := fmt.Sprintf("%s?%s", c.baseURL, params.Encode())

    req, err := http.NewRequestWithContext(ctx, http.MethodGet, endpoint, nil)
    if err != nil {
        return nil, fmt.Errorf("failed to create request: %w", err)
    }
    req.Header.Set("User-Agent", c.userAgent)
    req.Header.Set("Accept-Encoding", "gzip,deflate")

    resp, err := c.httpClient.Do(req)
    if err != nil {
        return nil, fmt.Errorf("wikidata search failed: %w", err)
    }
    defer resp.Body.Close()

    // ... standard response parsing pattern from YouTube client
}
```

### GORM Upsert Pattern for Category

```go
// Source: Modeled after GetOrCreateByURL in gorm_content_repository.go
func (r *GormCategoryRepository) Upsert(ctx context.Context, category *domain.Category) (*domain.Category, error) {
    model := categoryDomainToModel(category)

    err := r.db.WithContext(ctx).
        Clauses(clause.OnConflict{
            Columns:   []clause.Column{{Name: "wikidata_qid"}},
            DoUpdates: clause.AssignmentColumns([]string{"label", "description", "entity_type", "updated_at"}),
        }).
        Create(model).Error
    if err != nil {
        return nil, fmt.Errorf("failed to upsert category: %w", err)
    }

    // Fetch fresh record with DB-generated timestamps
    var fresh CategoryModel
    if err := r.db.WithContext(ctx).Where("wikidata_qid = ?", model.WikidataQID).First(&fresh).Error; err != nil {
        return nil, fmt.Errorf("failed to fetch upserted category: %w", err)
    }

    return categoryModelToDomain(&fresh), nil
}
```

## Open Questions

1. **Content.primaryCategory field resolution strategy**
   - What we know: A single FK (primary_category_id) on the content table points to the categories table. The simplest approach is a LEFT JOIN or GORM Preload.
   - What's unclear: Whether to use GORM Preload in the List query (eager load) or a separate field resolver (lazy load). Eager is simpler but loads category data even when not requested by the GraphQL query.
   - Recommendation: Use GORM Preload since it's a single FK (not N+1 risk for the FK itself). This adds a single LEFT JOIN. If the column is not requested in the GraphQL query, gqlgen won't call the field resolver, but the SQL still joins. Accept this minor overhead for simplicity. Alternatively, a field resolver with per-request batching is cleaner but more complex for a single FK.

2. **SetPrimaryCategory mutation vs. UpdateContent mutation**
   - What we know: CONTEXT.md says "no category CRUD mutations needed -- categories are created implicitly on selection." This implies a dedicated mutation for assigning categories to content.
   - What's unclear: Whether to add a new `setPrimaryCategory` mutation or extend the existing content update flow.
   - Recommendation: Dedicated `setPrimaryCategory` mutation. It's cleaner, handles the upsert-then-assign flow atomically, and doesn't pollute the content update path.

3. **Category column responsive tier**
   - What we know: The existing responsive tiers are xs (Item, Type, Perspectize), sm (+Channel), md (+Duration, Date), lg (+Views, Likes, Tags).
   - What's unclear: Which tier should show the Category column.
   - Recommendation: Add Category to the `sm` tier (445px+). It's a short text column (category label) that's important context. Place it after Type, before Channel in column order.
